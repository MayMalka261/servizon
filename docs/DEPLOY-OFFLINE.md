# העברה לרשת סגורה

המערכת תוכננה מלכתחילה להתקנה ברשת ללא גישה לאינטרנט. מסמך זה מסביר מה נעשה
כדי לאפשר זאת, ומה הנוהל בפועל.

---

## מה כבר טופל בקוד

| סיכון | הטיפול |
|---|---|
| פונט מ-CDN | Heebo **ארוז מקומית** ב-`frontend/public/fonts/`. קישור ל-`fonts.googleapis.com` נכשל בשקט ברשת סגורה ומפיל את כל הטיפוגרפיה לגיבוי סריפי |
| קריאות לענן | אין. אין Firebase, אין Supabase, אין API ציבורי |
| CDN לספריות | הכול נארז ב-bundle. אין `<script src="https://...">` |
| מקורות חיצוניים | `Content-Security-Policy` ב-`index.html` חוסם כל origin חיצוני. הפרה מופיעה כשגיאת קונסול בפיתוח, לא כתקלה שקטה אחרי ההעברה |
| שני שירותים לתחזק | ה-Frontend נבנה ל-static ומוגש מ-FastAPI. **פורט אחד, תהליך אחד** |
| טלמטריה | אין. הלוגים נכתבים לקובץ מקומי מסובב בלבד |
| כתיבה למסד הייצור | תרחישים נשמרים ב-SQLite מקומי **נפרד**. למסד הקריאה אין נתיב כתיבה |

כל התלויות בקוד פתוח וננעלות ב-`requirements.txt` וב-`package-lock.json`.

## נוהל ההעברה

### במחשב מחובר לאינטרנט

```bash
# פעם אחת, אם קובצי הפונט חסרים
python scripts/vendor_fonts.py

python scripts/build_offline_bundle.py
```

נוצרת התיקייה `offline-bundle/` הכוללת:

```
offline-bundle/
├── wheels/               כל חבילות ה-Python
├── backend/              קוד + נתוני seed + coefficients
├── frontend/dist/        ה-UI הבנוי (כולל הפונטים)
├── scripts/
├── docs/
└── INSTALL-OFFLINE.txt   הפקודות המדויקות לצד השני
```

### ברשת הסגורה

```bash
cd backend
python -m venv .venv
.venv\Scripts\activate

# מהגלגלים הארוזים בלבד — שום דבר לא יורד
pip install --no-index --find-links ../wheels -r requirements.txt

.venv\Scripts\python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

הכול זמין ב-`http://<host>:8000` — API ו-UI באותו שירות.

## חיבור למסד הנתונים האמיתי

ב-`backend/.env`:

```
SERVIZON_DATA_SOURCE=sql
SERVIZON_DATABASE_URL=mssql+pyodbc://user:pw@host/db?driver=ODBC+Driver+18+for+SQL+Server
```

עבור SQL Server נדרש `pyodbc` — יש לכלול אותו ב-`requirements.txt` **לפני**
בניית ה-bundle, אחרת הגלגל שלו לא ייארז.

לאימות שההחלפה עובדת:

```bash
.venv\Scripts\python -m pytest tests/test_repositories.py -q
```

הבדיקה מריצה את אותו ETL ואותו מנוע מול שני המקורות ומוודאת Snapshot זהה.

## בדיקות קבלה אחרי ההעברה

- [ ] `/api/health` מחזיר `status: "ok"` ו-`last_refresh` עדכני
- [ ] רשימת המוקדים נטענת ומציגה מגוון סטטוסים
- [ ] גרירת מנוף מזיזה את כל ה-KPI בכיוון הנכון
- [ ] **העברית מוצגת ב-Heebo ולא בגיבוי סריפי** — אם לא, `public/fonts/` חסר
- [ ] בקונסול הדפדפן, לשונית Network: **אפס בקשות ל-host חיצוני**
- [ ] שמירת תרחיש והשוואה עובדות, והשמות בעברית נשמרים כראוי
- [ ] `pytest -q` עובר במלואו
- [ ] רענון רקע (או `POST /api/refresh`) **אינו מאפס תרחיש פתוח**

הבדיקה האחרונה היא הדרישה המרכזית של המערכת ושווה לוודא אותה ידנית: פתח מוקד,
הזז מנוף, המתן לרענון, וודא שערכי המנופים נשארו במקומם.

## אבטחה

- אין תעבורה יוצאת. כל המידע נשאר במכונה.
- כל קלט עובר ולידציה ב-Pydantic, כולל הצמדה לגבולות המנופים.
- שגיאות בלתי צפויות מוחזרות כהודעה גנרית בעברית; ה-stack trace נכתב ללוג
  המקומי בלבד ולעולם לא מגיע לדפדפן.
- שמות טבלאות ועמודות בשאילתות מגיעים מקבועים בקוד, לא מקלט משתמש.
- המערכת קוראת בלבד ממקור הנתונים.

**מה שאינו כלול:** אין שכבת אימות משתמשים. ההנחה היא שהמערכת מוגנת ברמת הרשת.
אם נדרש אימות פר-משתמש, יש להוסיף אותו כ-middleware ב-`app/main.py` לפני
העלייה לאוויר.
