# מודל הסימולציה

מסמך זה מתאר את המודל המתמטי שמאחורי Servizon: מה כל מנוף עושה, איך מחושב כל
KPI, ומהן ההנחות שמגבילות את תוקף התוצאות. הוא נכתב כדי שאפשר יהיה להגן על כל
מספר שהמערכת מציגה מול קצין תפעול — לא רק להריץ אותו.

**עקרון מנחה:** המערכת אינה מכפילה מדדים במקדמים שרירותיים. המנופים משנים את
*גורמי הקלט התפעוליים* בלבד (נפח, זמן טיפול, מצבת), ומדדי השירות — זמן המתנה,
SLA, תפוסה, אורך תור — נגזרים מהם באמצעות **Erlang C**. זו הסיבה שהמודל נשאר
עקבי כאשר כמה מנופים זזים יחד: אין נתיב שבו שני מנופים "מתקנים" את אותו מדד
פעמיים.

## 1. ליבת המודל — Erlang C

`backend/app/simulation/erlang.py`

מודל התורים התקני של מרכזי שירות (M/M/c). הקלט הוא עומס בשעת השיא, זמן טיפול
ומספר נציגים זמינים; הפלט הוא התפלגות ההמתנה.

### עומס מוצע (Traffic, ביחידות ארלנג)

```
a = λ · AHT / 3600
```

כאשר `λ` הוא פניות לשעה ו-`AHT` בשניות. `a` הוא מספר השיחות המתנהלות בו-זמנית
בממוצע.

### הסתברות המתנה

Erlang B מחושב ברקורסיה יציבה נומרית (הנוסחה הסגורה עולה על גדותיה כבר במאות
נציגים):

```
B(0, a) = 1
B(n, a) = a·B(n-1, a) / (n + a·B(n-1, a))
```

ומכאן Erlang C:

```
ρ = a / N
C = B / (1 − ρ(1 − B))
```

### מדדי השירות

```
ASA        = C · AHT / (N − a)              זמן המתנה ממוצע
SLA(T)     = 1 − C · e^(−(N−a)·T/AHT)       שיעור המענה בתוך T שניות
Occupancy  = a / N                          תפוסת נציגים
Lq         = C · a / (N − a)                אורך תור ממוצע
```

כאשר `N ≤ a` המערכת אינה יציבה — התור גדל ללא גבול. המימוש מחזיר `is_overloaded`
ומחזיר ערכי קצה חסומים במקום אינסוף, וה-UI מציג התרעה קריטית מפורשת. **הערכים
המוצגים במצב זה הם רצפה, לא תחזית.**

### מצבת נדרשת

`required_agents` מוצא את ה-`N` המינימלי שעומד ביעד. מכיוון ש-SLA מונוטוני
עולה ב-`N`, החיפוש הליניארי מעל נקודת היציבות מחזיר את המינימום האמיתי.
התוצאה מוחזרת כמצבת *מתוקננת* (כלומר לאחר הוספת ה-shrinkage חזרה).

### נטישה

Erlang C עצמו אינו מודל נטישה. הנטישה מחושבת בנפרד לפי סבלנות מעריכית
(בסגנון Erlang A):

```
Abandonment = 1 − e^(−ASA / (patience · queue_tolerance))
```

`patience` **אינו קבוע גלובלי** — הוא נאמד לכל מוקד בנפרד מתוך ההיסטוריה שלו,
על ידי היפוך הנוסחה מול הנטישה וזמן ההמתנה שנצפו בפועל (`fit_patience`). כך
המודל מכויל לפונים של אותו מוקד ולא לממוצע ארצי.

## 2. גרף החוקים

`backend/app/simulation/rules.py`

כל חוק מצהיר מה הוא קורא ומה הוא כותב. המנוע ממיין טופולוגית ומריץ. הוספת מדד
חדש = הוספת חוק, בלי לגעת במנוע.

```
מנופים
  ├─→ זמן טיפול אפקטיבי ──┐
  ├─→ FCR אפקטיבי ────────┤
  ├─→ הסטת נפח ───────────┤
  │                        ↓
  │                   נפח פניות לנציג
  │                        ↓
  │                   עומס שעת שיא
  ├─→ נציגים זמינים ──────┤
  │                        ↓
  │                    Erlang C ──→ המתנה · SLA · תפוסה · אורך תור
  │                        ↓
  └─→ סבלנות מול תור ──→ נטישה
                           ↓
                    שביעות רצון לקוחות
```

### 2.1 הסטת נפח

```
survival = Π (1 − Δlever · e_lever)
λ_daily  = base_contacts · survival
```

המכפלה מכוונת. חיבור של ארבעה מנופי הסטה יכול לעבור 100% ולהוריד את הנפח
מתחת לאפס; במכפלה כל מנוף מסיט חלק ממה שנשאר אחרי קודמיו — חסום מלמטה, וקרוב
יותר לאופן שבו התוכניות האלה באמת מצטברות בשטח.

המנופים המסיטים: אימוץ דיגיטלי, שירות עצמי, שימוש לקוח ב-AI, רמת אוטומציה.

### 2.2 פניות חוזרות

פנייה שלא נסגרה במגע הראשון חוזרת. זה מה שהופך את FCR למנוף **נפח** ולא רק
למדד איכות:

```
repeats(f) = 1 + (1 − f) · repeat_factor
λ_total    = λ_daily · repeats(FCR_תרחיש) / repeats(FCR_בסיס)
```

**הנרמול מול הבסיס הכרחי.** הנפח הנצפה בהיסטוריה *כבר מכיל* את הפניות החוזרות
של היום. הכפלה בגורם הגולמי סופרת אותן פעמיים ומנפחת כל מוקד ב-20%–30% — מספיק
כדי להפיל מוקד תקין מעבר לצוק של Erlang ולדווח על קריסה שאינה מתרחשת. זה היה
באג אמיתי שנתפס בכיול מול הנתונים.

### 2.3 שעת שיא

Erlang C הוא מודל מצב-יציב. הזנת ממוצע יומי הייתה מחליקה בדיוק את השיא שמפיל
את רמת השירות. לכן המודל מופעל על שעת השיא:

```
peak_share = (peak_hour / daily)_בסיס · (hours_בסיס / hours_תרחיש)^flattening
λ_peak     = λ_total · peak_share
```

הרחבת שעות פעילות פורסת את אותו ביקוש על חלון רחב יותר ומשטחת את השיא.

### 2.4 זמן טיפול ו-FCR

```
AHT  = AHT_lever · (1 − [Δagent_ai·e₁ + Δkb·e₂])
FCR  = FCR_lever +  Δagent_ai·e₃ + Δkb·e₄
```

ההשפעות נמדדות כ**דלתא מול הבסיס**, כך שמנוף ה-AHT עצמו נשאר העוגן והמנופים
המסייעים מבטאים רק שינוי ממצב המוקד היום.

### 2.5 נציגים זמינים

```
N = agents_scheduled · (1 − shrinkage)
```

נציג בתדריך אינו עונה לטלפון. ה-shrinkage מוסר לפני Erlang ומוחזר בחישוב
המצבת הנדרשת.

### 2.6 שביעות רצון

מורכבת מול **נקודות ייחוס קבועות**, לא מול הבסיס של המוקד עצמו:

```
CSAT = base
     + (SLA − 0.85)·w₁
     + (FCR − 0.75)·w₂
     − (Abandon − 0.05)·w₃
     − ((ASA − 60)/180)·w₄
```

הבחירה בנקודות ייחוס קבועות עושה שתי עבודות: מוקד שרץ היום ב-50% SLA מדווח על
שביעות רצון נמוכה באמת במקום על "ממוצע" שזז רק כשנוגעים במנוף; ומכיוון שנקודות
הייחוס קבועות, תרחיש ריק משחזר את המצב הנוכחי במדויק, ללא מקרה קצה.

## 3. המקדמים

`backend/config/coefficients.yaml`

כל מקדם נקרא כך: *"תזוזה מלאה של המנוף מ-0 ל-1 משנה את גורם היעד בשיעור זה."*
מקדם הסטה 0.55 פירושו שהעלאת אימוץ דיגיטלי מ-0% ל-100% מסירה 55% מנפח הטלפון.

המקדמים נטענים לפי **סוג מוקד**, עם ירושה חלקית מ-`default`. מוקד רפואי מקבל
מקדמי הסטה נמוכים בהרבה — שאלה קלינית מתנגדת לשירות עצמי הרבה יותר משאלה
מנהלתית.

הם יושבים ב-YAML ולא בקוד כדי שאנליסט יוכל לכייל מול היסטוריה בלי פריסה.

## 4. הנחות ומגבלות

יש להצהיר עליהן במפורש, כי הן תוחמות את הטווח שבו התוצאות תקפות:

1. **הגעות פואסון, זמני טיפול מעריכיים, נציגים זהים.** ההנחות הסטנדרטיות של
   M/M/c. מוקד עם תורים מיומנויות (skill-based routing) יסטה מהן.
2. **מצב יציב בתוך המקטע.** המודל מתאר שעת שיא יציבה, לא גל פתאומי.
3. **תוצאה חדה סביב הצוק.** ב-Erlang C, מוקד בתפוסה 96% מגיב באופן דרמטי
   לתוספת קטנה של נציגים. זו התנהגות אמיתית של המודל ולא באג — אבל היא אומרת
   שדיוק הקלט קריטי דווקא במוקדים העמוסים.
4. **המקדמים הם אומדנים.** ערכי ברירת המחדל סבירים אך אינם מכוילים מול נתוני
   צה"ל. יש לכייל אותם מול היסטוריה אמיתית לפני שימוש בהחלטות תקציב.
5. **תרשים המפל מתעלם מאינטראקציות.** כל עמודה היא המנוף לבדו מול הבסיס.
   הסכום המשולב המוצג בכרטיסי ה-KPI הוא הקובע.
