# ארכיטקטורה

## תמונת מצב

שני שירותים בפיתוח, **תהליך אחד בפריסה**. ה-Frontend נבנה ל-static ומוגש על ידי
FastAPI — פורט אחד, בלי reverse proxy. זו החלטה שנועדה להתקנה ברשת סגורה: ככל
שיש פחות רכיבים להגדיר, כך פחות דברים יכולים להישבר בהעברה.

## החלטה 1 — הפרדת נתונים חיים מתרחיש

זו הדרישה המרכזית של המערכת והקלה ביותר לשבירה. מימוש נאיבי היה מחזיק את ערכי
המנופים ב-cache של React Query; רענון רקע היה מחליף את הנתונים ומוחק את עבודת
המשתמש באמצע ניתוח.

המימוש בפועל:

| | בעלים | היכן | מה קורה ברענון |
|---|---|---|---|
| **בסיס חי** | השרת | React Query, `refetchInterval` | מוחלף |
| **תרחיש** | הלקוח | Zustand `leverStore` | **נשמר** |

הגשר היחיד הוא `syncBaseline`. ה-store עוקב אחרי אילו מנופים המשתמש *נגע* בהם:

- מנוף שלא נגעו בו — עוקב אחרי הבסיס החדש. הוא אמור לשקף את המציאות.
- מנוף שנגעו בו — **נשאר בדיוק במקומו**. זו עבודת המשתמש.

התוצאה מחושבת מחדש מול הבסיס החדש, והודעה עדינה מסבירה למה המספרים זזו. רענון
מרגיש כמו עדכון נתונים, לא כמו איפוס הכלי.

כל Snapshot נושא `id` הנגזר מהתוכן שלו. רענון שלא שינה דבר מחזיר את אותו `id`,
כך שהמשתמש לא מקבל התרעת "הנתונים השתנו" ללא סיבה.

## החלטה 2 — מנוע אחד, בצד השרת

המנוע יושב ב-Python בלבד. שכפול הלוגיקה ל-TypeScript עבור תצוגה מקדימה מיידית
היה יוצר שני מימושים של אותו מודל, ואיתם סיכון ודאי ל-drift: שתי גרסאות של
נוסחת Erlang שמתפצלות אחרי החוק השלישי שמישהו מוסיף.

הגרירה עוברת debounce של 120ms ומריצה סיבוב לשרת. Erlang C הוא חישוב של
מיקרו-שניות, וברשת מקומית הלולאה נסגרת מתחת ל-10ms. `keepPreviousData` שומר את
הכרטיסים מלאים בזמן החישוב, כך שהם מונפשים מערך לערך במקום לקרוס לשלד.

אם בשטח יתגלה lag, אפשר להוסיף mirror ב-TS ל-preview אופטימי — אבל לא משלמים
את מחיר הכפילות מראש.

## החלטה 3 — נתוני המקור אינם משתנים

שלוש שכבות הגנה, לא הצהרה בתיעוד:

1. **מודלים קפואים.** `Snapshot` ו-`BaselineMetrics` הם `frozen=True` בפידנטיק.
   סימולציה *לא יכולה* לשנות אותם — זו ערבות ברמת הטיפוס.
2. **Repository לקריאה בלבד.** הממשק חושף רק פעולות `load_*`. אין נתיב כתיבה.
3. **אחסון נפרד לתרחישים.** תרחישים נשמרים ב-SQLite מקומי משלהם, לא במסד
   הקריאה. הפניית האפליקציה למסד ייצור לעולם לא מסכנת כתיבה אליו.

## החלטה 4 — החלפת דור אטומית

הרענון בונה מערך נתונים חדש *בצד*, ומחליף אותו בהשמה אחת. קוראים רואים תמיד דור
אחד עקבי — לעולם לא חצי ישן וחצי חדש. רענון שנכשל משאיר את הדור הקודם משרת
תעבורה, והשגיאה מדווחת ב-`/api/health`.

## החלטה 5 — Repository מופשט

`ServiceDataRepository` הוא הגבול בין "מאיפה הנתונים" ל"מה עושים איתם". מימושי
CSV ו-SQL קיימים שניהם, ו-`tests/test_repositories.py` מריץ את **אותו ETL ואותו
מנוע** על שניהם ומוודא Snapshot זהה בייט-לבייט.

זה הופך את המעבר ל-SQL Server ממשימת מיגרציה לשינוי של שורת קונפיגורציה —
ומוכיח זאת היום, לא ביום ההעברה.

## מבנה הקוד

```
backend/app/
  api/routes/      נקודות קצה HTTP — דקות, בלי לוגיקה עסקית
  domain/          enums ומודלי Pydantic (חוזה ה-API)
  repositories/    ממשק גישה לנתונים + מימושי CSV/SQL
  services/        ETL, מאגר Snapshot, scheduler, אחסון תרחישים
  simulation/      Erlang C, גרף חוקים, מנוע, מנופים, המלצות
  core/            logging

frontend/src/
  app/             router, providers
  pages/           שלושה מסכים
  components/      ui · centers · levers · kpi · charts · scenarios · layout
  hooks/           גישה לנתונים
  services/        לקוח HTTP
  stores/          leverStore — מצב התרחיש
  simulation/      פורמט ערכים, צבעי אקסנט
  types/           חוזה ה-API (מראה ל-Pydantic)
```

**כלל:** קומפוננטה אחת = תפקיד אחד. הלוגיקה יושבת ב-hooks ובשכבת ה-simulation,
לא בתוך JSX.

## ביצועים

| טכניקה | היכן | למה |
|---|---|---|
| Virtualization | רשימת המוקדים | עשרות עד מאות מוקדים ביעד |
| `keepPreviousData` | סימולציה, רשימה | כרטיסים לא קורסים בכל תזוזת סליידר |
| Debounce | גרירת מנוף | בקשה אחת בסוף התנועה, לא שישים במהלכה |
| `React.lazy` | מסכי סימולציה והשוואה | Recharts ו-Framer Motion לא נטענים במסך הראשון |
| Manual chunks | build | שינוי קוד לא מאלץ הורדה מחדש של כל Recharts |
| `useMemo` | טרנספורמציות גרפים | ריצה מחדש רק כשהנתונים זזים |
| Cache בזיכרון | Snapshot | ה-ETL רץ פעם ב-N דקות, לא בכל בקשה |
